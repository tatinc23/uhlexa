## Headline findings (the ones that change the build)

1. The official SDK/CLI exist and are current: PyPI `inkbox` **0.7.20** (2026-10-21), npm `@inkbox/cli` and `@inkbox/sdk` **0.7.20** (2026-10-21), crates.io `inkbox` 0.7.20. Python >=3.11, MIT, synchronous only.
2. **Calls: Uhlexa CAN answer every turn of a phone call.** Use the bring-your-own tier: Inkbox opens a `wss://` WebSocket to our server, does speech-to-text and text-to-speech itself, and sends us `transcript` events; we stream `text` deltas back. Inkbox's own "Voice AI" (hosted agent) is a fixed, opinionated model with no custom tools and no custom-LLM URL. There is no OpenAI-compatible-URL option and no per-utterance webhook option.
3. **Webhook signature**: header `X-Inkbox-Signature: sha256=<hex>` = HMAC-SHA256 over `{X-Inkbox-Request-ID}.{X-Inkbox-Timestamp}.{raw_body}` with the **per-identity** signing key; docs say reject if timestamp is more than 300 s off. The SDK's `verify_webhook` does NOT enforce the 300 s window (checked in source); we must add it.
4. **Multi-identity**: one org-admin key can send/read/place calls as any identity (calls, iMessage and webhooks take `agent_identity_id`; mail/SMS are addressed by mailbox/number). But the **A2A protocol endpoint rejects admin keys**: each A2A sender needs its own identity-scoped, claimed key. Admin keys can only be minted in the Console by a human. This repo has no admin key (only `INKBOX_SAMANTHA_KEY`).
5. **Reality check on "100 identities with phone plans"**: the published Startup plan is 100 identities but only **9 dedicated VoIP numbers + 1 dedicated iMessage number**; the other identities get shared iMessage (including calls over the shared iMessage line, no transfers). I could not see Ken's actual plan (billing is admin-only; 403 with the scoped key). The only org-level fact I can see: one dedicated iMessage line exists (`<Uhlexa iMessage line>`, attached to an identity whose handle my key cannot see).
6. @samantha (the only identity I can authenticate as) has **no phone number**: `sms_available:false`, `calling_available:false`. Shared iMessage is enabled and works recipient-first.

## 2. Inbound: how our server receives email / SMS / iMessage / calls

Three mechanisms: signed webhooks (primary), polling (list endpoints above, authoritative catch-up), and the call media WebSocket (calls only). MCP Events also exist but need identity-bound OAuth and host support ([docs] mcp-server); skip.

### Webhook registration ([docs] api/webhooks/subscriptions, [openapi])
- `POST https://inkbox.ai/api/v1/webhooks/subscriptions` (admin key, or a claimed agent key for its own identity). Body: `{"agent_identity_id": "<uuid>", "url": "https://...", "event_types": ["message.received","text.received","imessage.received","call.ended","a2a.task.created"], "context_config": null, "auth_token": null}`. Response `201`: the subscription (`id, organization_id, agent_identity_id, owner_identity_id, url, event_types, context_config, auth_token, has_auth_token, status:"active", created_at, updated_at`) plus a one-time **`signing_key`** (non-null only if this identity had no key yet).
- Rules: `url` must be **HTTPS**; non-empty distinct `event_types` (any mix of the 44 notification types; the live catalog lists 45 entries including `phone.incoming_call`); **max 60 active subscriptions per identity** (61st -> 409); one subscription per identity may mix all channels (`GET /api/v1/webhooks/catalog` -> `supports_identity_subscriptions: true` [live]); use `?scope=identity` on update/delete of mixed subscriptions. `auth_token` makes every delivery also carry `Authorization: Bearer <token>`. `context_config` (`{"email"|"texts"|"calls": {"mode":"count","count":N<=50} | {"mode":"window","hours":H<=168}}`) adds `data.context` history to received events only.
- Event types we need: `message.received|sent|delivered|bounced|failed|forwarded`, `text.received|sent|delivered|delivery_failed|delivery_unconfirmed`, `imessage.received|reaction_received|sent|delivered|delivery_failed`, `call.ended`, `a2a.task.created|message|canceled`, `a2a.sent_task.updated`. (`phone.incoming_call` is NOT subscribable; it is the synchronous callback below.)
- Public URL requirement: HTTPS, publicly reachable by Inkbox. For a call WebSocket: `wss://`. Redirects are not documented. For local dev, Inkbox tunnels give `https://{handle}.inkboxwire.com` (every identity owns one tunnel; @samantha's is live and is how her gateway receives events).

### Envelope and payload shapes ([docs] + [live] catalog examples; every example has a top-level `id`)
```json
{"id":"evt_8f2c1a9b-7d6e-4f4a-b2c1-d0e94b21c377","event_type":"message.received","timestamp":"2026-04-10T18:13:42.201Z",
 "data":{"message":{"id":"<uuid>","mailbox_id":"<uuid>","email_address":"support@inkboxmail.com","thread_id":"<uuid>","message_id":"<rfc5322>","from_address":"customer@example.com","to_addresses":["..."],"cc_addresses":[],"bcc_addresses":null,"subject":"...","snippet":"...","body":"plain text, may be truncated","body_state":"complete","body_truncated":false,"direction":"inbound","status":"received","has_attachments":false,"created_at":"..."},
         "contacts":[{"bucket":"from","address":"...","id":"<uuid>","name":"Jane Doe"}],"agent_identities":[]}}
```
- `text.received`: `data.text_message{id,direction,local_phone_number,remote_phone_number,text,type:"sms|mms",media,is_read,delivery_status,conversation_id,sender_phone_number,recipients,created_at,...,sender_access?}`, `data.contacts[{id,name,memories[]}]`, `data.agent_identities[]`, `data.recipient_phone_number` (null for 1:1).
- `imessage.received`: `data.message{id,conversation_id,reply_to_message_id,thread_id,thread_root_message_id,assignment_id,direction,remote_number,sender_number,participants,is_group,content,message_type,service:"imessage|sms|rcs",send_style,media,was_downgraded,status,error_*,is_read,recipients,reactions,created_at,updated_at,sender_access?}`, `data.reaction:null`, `data.contacts`, `data.agent_identities`. On dedicated lines `remote_number` can be a non-phone address (email); those threads are receive-only (sending returns `422 recipient_not_e164`).
- `call.ended`: `data{call{id,origin,local_phone_number,remote_phone_number,direction,status,mode:"client_websocket|hosted_agent",hosted_agent_authority_mode,on_voicemail,reason,hangup_reason,started_at,ended_at,duration_seconds,connections,forwardings},outcome (null for client_websocket),post_call_action_items[],contacts,agent_identities,transcript{entries[{party,phone_number,text,ts_ms}|{marker:"abridged",omitted_turns,omitted_ms}],abridged,url},transcript_url}`. Never-connected client-websocket calls do NOT fire it; Voice AI calls fire on every terminal state.
- `a2a.*`: `data{task_id,context_id,state,caller{identity_id,organization_id,handle},message_id?,parts?[{text}|{data}]}`.
- Delivery semantics: fire-and-forget POST, response body ignored, respond 2xx fast and work async. Delivery is at least once; dedupe on the envelope `id` (stable across retries and replays; the delivery log's `event_id` equals it). A2A docs say retries are "bounded". **Retry schedule and request timeout for fire-and-forget events are not documented.** Missed deliveries: `GET /api/v1/webhooks/deliveries?subscription_id=&success=false` then `POST /api/v1/webhooks/deliveries/{delivery_id}/replay` (replayable events only; Companion/Slack/incoming-call not replayable). Polling the list endpoints is the authoritative catch-up.
- The **synchronous incoming-call callback** (only if `incoming_call_action="webhook"`): flat payload (no envelope) `{id, origin, local_phone_number, remote_phone_number, direction:"inbound", status:"initiated", client_websocket_url, rate_limit, contacts[], agent_identities[]}`; we must reply `200 {"action":"answer"|"reject","client_websocket_url":"wss://..."?}` **within 10 seconds**; non-200, invalid body or timeout is treated as `ignore` ([openapi]). No `auth_token` support on this one. Simpler alternative: `auto_accept` with a fixed `client_websocket_url` per identity.

### Signature verification ([docs] api/phone/webhooks, api/mail/webhooks, signing-keys; [sdk-src] `signing_keys.py`)
- Headers on every signed delivery: `X-Inkbox-Request-ID` (UUID), `X-Inkbox-Timestamp` (Unix seconds), `X-Inkbox-Signature: sha256=<lowercase hex>`.
- Algorithm: `HMAC_SHA256(key = signing_key (strip optional "whsec_" prefix), msg = f"{request_id}.{timestamp}.".encode() + raw_body_bytes)`; compare hex digest of the part after `sha256=` with `hmac.compare_digest`. Use the **raw body bytes**, never a re-serialized parse.
- Tolerance: docs say reject if `abs(now - timestamp) > 300` seconds. **The SDK's `verify_webhook(payload=bytes, headers=Mapping, secret=str) -> bool` does not check the timestamp** (only prefix + HMAC); add the 300 s check ourselves. Header lookup in the SDK is case-insensitive.
- Secret source: **one signing key per agent identity** (not per org, not per subscription). Created automatically on the first subscription for a keyless identity (returned once in `signing_key`) or explicitly with `POST /api/v1/identities/{handle}/signing-key` (also **rotates** if one exists; old key dies immediately). `GET .../signing-key` returns `{configured, created_at}` only. Until a key exists, that identity's webhooks and WebSocket upgrades are sent **unsigned**. Because the key is per identity and nothing in the headers names the identity, route by URL: one subscription per identity with a handle in the path (e.g. `/webhooks/inkbox/{handle}`) and look up that identity's secret.
- WebSocket upgrade signing ([docs] media-stream, [sample]): same three headers on the handshake; the signed "body" is the **exact value of the `X-Call-Context` header** (`verify_webhook(payload=call_context.encode(), headers=..., secret=...)`). Reject with close code 1008 on failure.
- Test vector: Inkbox publishes only header *shapes* (catalog `example_signature_headers`), no secret+body+digest triple. A locally computed vector from the documented algorithm (fake secret, NOT an Inkbox-published value): secret `test-signing-key-not-real`, request id `11111111-2222-4333-8444-555555555555`, timestamp `1764875501`, body `{"id":"evt_test","event_type":"text.received","data":{}}` -> `sha256=3eaa19b490af8a45bb010d12a78c68987f478619dc180aba3236e6ef74f767d1` (identical with or without a `whsec_` prefix on the secret).

## 3. Phone calls in depth

### Can an identity answer inbound and place outbound calls with a voice agent? Yes, two tiers ([docs] hosted-call-agent: "exactly two ways to put a brain on a call")
**Tier A: Inkbox Voice AI** (`incoming_call_action="hosted_agent"`, or outbound `mode="hosted_agent"` + `reason`; labeled beta). Inkbox runs the realtime voice model; opinionated, fixed built-in toolset (transfer/conference on dedicated lines, DTMF, action items, text/iMessage/email the caller, contacts and history lookup per authority mode). **"It also doesn't run custom tools"**; no custom system prompt beyond up to 8,000 chars of `instructions`; no way to substitute our model or hit our systems mid-call. Output: a `call.ended` package with transcript, `outcome` and `post_call_action_items`. The vendor model is not named in the docs (the voice catalog has OpenAI-style ids `alloy, ash, ballad, coral, echo, sage, shimmer, verse, marin, cedar` plus `ara, eve, rex, thalia, andromeda, orion, talia, eddie, eldrin`; @samantha's config reports `effective_voice: "marin"`, `effective_model: "gpt-live-1"`, which the docs say to treat as an opaque compatibility value). **This is not the Uhlexa brain.** Default authority mode is `yolo` (can read/send across ALL the identity's contacts, email, SMS, iMessage, calls) unless a mode was explicitly saved; set `contact_scoped` if ever used. New numbers default to `hosted_agent` for inbound.

**Tier B: bring your own over a WebSocket** (`incoming_call_action="auto_accept"` + `client_websocket_url`, or `webhook` action returning a URL, or outbound `place_call(client_websocket_url=...)`). **Each turn can be answered by our server.** Four modes picked by the handshake *response* headers ([docs] api/phone/media-stream):

| `X-Use-Inkbox-Speech-To-Text` | `X-Use-Inkbox-Text-To-Speech` | We receive | We send |
|---|---|---|---|
| true (default) | true (default) | `transcript` text | `text` deltas (Inkbox speaks them) |
| false | true | `media` raw audio | `text` (+ optional `transcript` for history) |
| true | false | `transcript` text | `media` audio + `audio_done` |
| false | false | `media` | `media` audio (+ `transcript`) (full bridge, e.g. to a realtime model) |

  Audio format header `X-Inkbox-Audio-Format`: `pcmu_8000` (default) or `pcm_s16le_16000` (little-endian despite the `L16` label); unsupported or repeated audio-format headers close the connection.

  Recommended for Uhlexa = row 1. Exact flow ([docs], [sample]):
  1. Inkbox connects to our `wss://` URL with headers `X-Call-Context` (JSON `{"call_id","phone_number","direction","contacts":[{"id","name"|null,"memories":[...],"memories_truncated"}]}`, <=8,000 bytes) and, if the identity has a signing key, `X-Inkbox-Request-ID/Timestamp/Signature`. We accept with `X-Use-Inkbox-Speech-To-Text: true` and `X-Use-Inkbox-Text-To-Speech: true`.
  2. `{"event":"start","stream_id":"abc","start":{"call_control_id":"v3:xyz","stream_id":"abc","media_format":{"encoding":"PCMU","sample_rate":8000,"channels":1}}}`
  3. Per utterance: `{"event":"transcript","text":"...","is_final":false|true,"turn_id":"turn_01"}` (interim then final). Act only on `is_final:true` (the sample does).
  4. We stream the answer: `{"event":"text","delta":"Your order shipped","done":false,"turn_id":"turn_01"}` ... then `{"event":"text","done":true,"turn_id":"turn_01"}`.
  5. Interruption: `{"event":"barge_in","trigger":"interim_transcript|final_transcript|cancel_turn","text":"...","tts_interrupted":true,"turn_id":"turn_02"}` -> stop generating immediately, then send `{"event":"clear"}` to flush queued audio.
  6. We can press keys `{"event":"dtmf","digits":"1"}` (1-30 chars of `0-9*#`, max 20 outstanding bursts, no ack) or hang up `{"event":"stop","reason":"agent_hang_up"}`; Inkbox sends `{"event":"stop","reason":"remote"}` when the call ends.
  7. Transcripts: Inkbox stores them automatically when it does the STT; in modes where we do STT/TTS we must send `{"event":"transcript","party":"remote|local","text":...,"is_final":true,"turn_id":...}` so they appear in call history.
- So yes, the same Uhlexa brain can answer calls: the WebSocket handler calls the same intent/routing code the web simulator uses, per final transcript, and streams text back. The sample does exactly this with `AsyncOpenAI.chat.completions.create(model="gpt-5.1", stream=True)`.

## 4. iMessage specifics

- Two lines ([docs] capabilities/imessage): **shared service** via the Inkbox router (human texts first) and **dedicated line** (org-owned, can start 1:1 and group chats). Org-owned shared pool/router is beta and request-only (`support@inkbox.ai`).
- Recipient-first connect flow: the human texts `connect @<handle>` to the router number. Resolve the number at runtime, never hardcode: `inkbox.imessages.get_triage_number()` / `GET /api/v1/imessage/triage-number` -> `{"number","connect_command","sms_link","connect_qr_png_data_url"}`. [live] today: number `+16504849720`, command `connect @samantha`, `ready:true` (MCP `inkbox_imessage_onboarding_get`). The router replies and sends the agent's contact card. One human can connect to several agents; each is its own conversation (pricing FAQ: a recipient can connect to **up to 3 agents at a time**).
- Enablement is opt-in per identity: `imessage_enabled=True` at create or `identity.update(imessage_enabled=True)`. Disabled identity: router will not connect people, sends rejected, inbound not delivered.
- Can an identity start an iMessage to someone who has not connected? **Shared service: no** (send to an unconnected number -> `404`; expired -> `409 imessage_connection_expired`). **Dedicated line: yes**, subject to contact rules, consent, and: first-contact limits **10 new recipients/hour and 40/24 h**; before the recipient's first reply every 1:1 message must be <=159 chars with no phone numbers, links or media, and at most **3 messages** until they reply (`422` codes `imessage_unanswered_followup_limit`, `imessage_reply_required_for_phone_numbers`, `imessage_reply_required_for_links_or_media`, `imessage_opening_message_too_long`). These pre-reply rules apply on every line type, including dedicated.
- Limits: each identity <=100 iMessages per rolling 24 h (`429` with `Retry-After`, `X-RateLimit-*`); plan caps on shared service ([pricing]): Free 2,000 msgs/mo and 3 unique recipients at a time; Developer 10,000 and 10; Startup 100,000 and 100. Shared connections auto-expire after 14 days old AND 14 days with no messages (history kept; recipient must reconnect; no notification). Dedicated lines/org pools do not expire.
- Group chats: **dedicated line only**, 2-8 distinct E.164 recipients, `send_imessage(to=[...])` creates; reply by `conversation_id` (`group_creation_status`: creating|not_created|ready); no add/remove-member API; read receipts and typing are 1:1 only; tapbacks, media and send styles work. Shared service is 1:1 only. Group MMS over SMS is a separate beta.
- Replies: `send_imessage(conversation_id=..., text=...)` only when `get_imessage_conversation(id).assignment_status == "active"` and the remote is E.164. Delivery transport may fall back to SMS/RCS (`service`, `was_downgraded` on the message). Tapbacks: `love, like, dislike, laugh, emphasize, question, eyes`; inbound can be `custom` emoji. `reply_to_message_id` threading needs SDK >=0.7.13. Media: upload <=10 MiB then send the URL; one URL per message.
- Contact rules (admin writes): identity-owned `phone_*_filter_mode` (default `blacklist`) governs SMS, calls and iMessage together; shared-line connect requires both inbound and outbound to be permitted.

## 7. A2A (identity-to-identity tasks)

- Protocol: A2A 1.0 JSON-RPC at `POST https://inkbox.ai/a2a/{handle}`; Agent Card at `GET https://inkbox.ai/a2a/{handle}/card` (public, no auth; @uhlexa's card returns 200 today). Headers: `X-API-Key` (claimed identity-scoped key), `A2A-Version: 1.0`, `Content-Type: application/json`. Card: `capabilities:{streaming:false,pushNotifications:false}`, default skill `general`, input/output `text/plain`, `application/json`. Streaming/push methods are unsupported.
- Send: Python `with identity.a2a_client() as a2a: target = a2a.fetch_card("https://inkbox.ai/a2a/<peer>/card"); r = a2a.send(target, text="...", message_id=None, context_id=None, task_id=None)`; `a2a.wait(target, task_id, timeout=120.0, interval=5.0)`. Raw: `{"jsonrpc":"2.0","id":1,"method":"SendMessage","params":{"message":{"messageId":"<uuid>","role":"ROLE_USER","parts":[{"text":"..."}],"contextId":"<optional>","taskId":"<optional>"},"configuration":{"returnImmediately":true}}}`. `messageId` doubles as idempotency key. Neither id -> new task in a new context; `contextId` only -> **sibling task in that context** (either participant may start it, so a second agent can resume a thread); `taskId` -> continue that task. Parts carry `text` or structured `data` (JSON), so payloads can include IDs/summaries as `data`. Limits: request body 1 MiB, 500 messages/task, 100 tasks/context. MCP tools `inkbox_a2a_task_send/reply/get/tasks_list/agents_list` exist for the same.
- Receive: task inbox is durable (works while the worker is offline). Webhooks `a2a.task.created|message|canceled` (worker side) and `a2a.sent_task.updated` (requester side; read `data.state`); payload gives `task_id, context_id, state, caller, message_id, parts` (only the triggering message), then fetch the full task. Polling: `identity.a2a_tasks(direction="inbound|outbound|both", requester_handle, worker_handle, state, context_id, q, since, cursor, limit=50)` / `iter_a2a_tasks`, `a2a_task(id)`, `a2a_sent_tasks()`, `a2a_messages(...)`, `a2a_contexts()`, `a2a_context(id)`, `a2a_update_context(id, name=)`. REST: `GET /api/v1/identities/{handle}/a2a/tasks`, `.../tasks/{task_id}`, `.../sent/tasks`, `.../contexts`, `.../messages`. Responses are `{items, next_cursor}`.
- Reply (worker): `identity.a2a_reply(task_id, intent="progress|ask_caller|complete|fail", text=None, parts=None)` -> `POST /api/v1/identities/{handle}/a2a/tasks/{task_id}/reply` body `{intent, parts[1..64]}`; states `submitted -> working -> input_required -> completed|failed|canceled` (wire spelling `TASK_STATE_*`). Replying to the webhook HTTP request itself does nothing. Admin keys can do ledger reads and replies; only protocol *sends* need the scoped key.
- Admission (second gate): same-org enabled identities may call each other without rules; cross-org private needs requester-outbound and worker-inbound allow rules (admin to create); explicit blocks win. New identities default to whitelist but same-org is admitted. [live] @samantha: A2A enabled, `filter_mode:"whitelist"`, one outbound allow rule for `aze`, `allow_public_egress:true`, `publicly_discoverable:false`, `outbound_task_count:10`.
- Self-A2A: **not documented either way.** [local] notes record that an identity sending to its own handle returned `422` on 2026-09-08 (`a2a_task_send target_handle:"samantha"`); I did not re-test because a send would create a task. A2A between *different* in-org handles works [local]. Each family member's agent must therefore be its own identity.
- Contexts as durable threads: each context has a name (auto-named from first message; either side can rename: 1-5 words, <=80 chars), stored on one canonical server-side ledger (no duplication), searchable by `q`. Context ids are not credentials: admission is re-evaluated per direction.

## Design implications

1. **Use Tier B (WebSocket, Inkbox STT+TTS) for calls; do not use Voice AI as the brain.** One `wss://` endpoint per deployment with a per-identity path (e.g. `/ws/phone/{handle}`): the handshake gives `X-Call-Context` (call_id, remote phone, contacts) but no explicit identity handle, so the path must carry it. Verify the handshake signature over the raw `X-Call-Context` value with that identity's signing key. Call turn handler: on `transcript` with `is_final:true` -> same Uhlexa turn pipeline as the simulator -> stream `text` deltas -> final `done:true`; on `barge_in` cancel the generation task and send `clear`. Keep replies short for speech; no markdown.
2. **Confirm WebSocket hosting first.** Manufact Cloud must terminate a public `wss://` and keep it open for up to 60 minutes (10 on Free); I did not verify this. Fallback: an Inkbox tunnel (`{handle}.inkboxwire.com`, edge TLS) or a second small WS host; in-process ASGI forwarding exists in the SDK (`inkbox.tunnels.connect(name, forward_to=app)`), but that requires a long-lived process, not serverless.
3. **Webhook receiver**: one route `POST /webhooks/inkbox/{handle}`; read `await request.body()` bytes before parsing; check `abs(now - X-Inkbox-Timestamp) <= 300`; HMAC with that handle's secret; dedupe on envelope `id`; enqueue a job and return 200 immediately (sync Postgres insert, then the worker does the work, since Keiki turns can be slow); the SDK client is sync so wrap calls in the worker. Persist each identity's signing key (returned once; encrypted env/secret store). Treat missing signature headers as a rejection once a key exists (the key being absent means unsigned traffic, which must also be rejected in production).
4. **Subscriptions per identity**: create one mixed subscription per family agent with `event_types` = `message.received, text.received, imessage.received, imessage.delivery_failed, call.ended, a2a.task.created, a2a.task.message, a2a.sent_task.updated`; capture `signing_key` from the create response in the same transaction. Use `auth_token` as a second factor on the URL.
5. **Set inbound call behavior explicitly at identity creation** (`auto_accept` + our wss URL, or `auto_reject`); never leave `hosted_agent`/`yolo` defaults on a family member's number.
6. **Channel realism per plan**: calls for most identities must ride the shared iMessage line (`origination="shared_imessage_number"`, requires the human to have connected first; no transfer/conference) because dedicated numbers are limited (Startup: 9 VoIP + 1 iMessage). SMS requires a number and START from each US recipient; so for the demo, plan SMS/voice for the identities that actually have numbers and iMessage/email for the rest. Count minutes: 300/month org-wide on Startup; $0.03/min after.
7. **iMessage onboarding step in the demo script**: each participant texts `connect @<handle>` to the router number read live from `get_triage_number()`; show `assignment_status`; handle `404`/`409 imessage_connection_expired` by telling the user how to reconnect. Initiating to an unconnected person is only possible from the single dedicated line and under the 3-message / 159-char / no-links rules.
8. **A2A is the right primitive for agent-to-agent handoff/resume**: model each persistent conversation as an A2A context; handoff = new sibling task in that `context_id` to the other agent's endpoint with `parts` containing text plus a `data` part (thread id, summary pointer). Receiver: webhook `a2a.task.created` -> job -> `a2a_task(id)` -> `a2a_reply(intent="complete", ...)`. Requires per-sender scoped keys (admin key rejected) and claimed identities; one agent cannot task itself (local note).
9. **Keys**: obtain a Console-minted admin key (human step), store as secret `INKBOX_ADMIN_API_KEY`; script identity creation (`create_identity`) then `api_keys.create(scoped_identity_id=...)`; store per-identity scoped keys and signing keys. Never reuse @samantha's key for Uhlexa traffic and never touch her subscriptions/signing key.
10. **Disclosure and consent baked into the product**: AI disclosure in the first turn of every call/thread; "this call is transcribed" notice; STOP/START wording; adults only; fictional data for seed families. Add these to `docs/COMPLIANCE.md` (this doc writes no other file).

2. **No phone number reachable from here.** @samantha has none, and no numbers are visible to my key; SMS/voice flows cannot be exercised or even listed until an admin provisions numbers (and confirms the plan allows them). Voice/SMS were therefore documented, not live-tested; no call was placed (not permitted).

4. **Plan mismatch risk**: "100 identities with phone plans" is not a published plan shape (Startup = 100 identities, 9 VoIP numbers, 1 dedicated iMessage). Confirm in the Console before designing per-member numbers.
5. **Recipient-side steps are manual**: every demo human must text `connect @handle` (shared iMessage) and, for SMS in the US, `START`. No API can do this for them.
